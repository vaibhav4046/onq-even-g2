# OpenBot backend feature map (ideas only) for OnQ

Date: 2026-11-26. Method: read-only look at the installed OpenBot 0.79.0 desktop app (file index, manifest, bundled skill docs, setting key names, public home page) and a quick read of the OnQ server code.

Licence note: OpenBot is PolyForm Noncommercial. This file copies no code, no assets and no text. Everything below is a description in our own words. OnQ must build each capability with its own code.

Privacy note: nothing under the OpenBot user-data folder was opened. Only folder and file names were listed. OpenBot was not run. The app bundle (`app.asar`) was read only as a file index plus keyword and identifier checks, with nothing extracted to disk.

## 1. Summary

OpenBot is a local-first desktop app that hosts many named agents. Each agent has its own instructions, workspace and chat history. Behind the agents sits a provider layer. It drives installed coding CLIs (Claude Code, Codex, Gemini, Grok, OpenCode, Cursor, Cline, Hermes and others), custom ACP agents, OpenAI-compatible endpoints and local model servers. When one provider hits a limit, an agent can fail over to another and keep its chat and files.

Around that core it adds a secrets vault, an approval layer with an agent-access level per server, routines and a visual workflow canvas (schedule, webhook, message, GitHub, Discord, Telegram and Slack triggers), long-term memory with a background review pass, local skills, an MCP client and server, a built-in browser agent, computer use, and a remote-desktop runtime. It also offers a shared agent database, static site hosting, voice in and out with local models, a phone link (relay or private network), team and hosted servers, and a 257-entry catalog of service plugins.

For OnQ the lesson is not to copy the app. The lesson is the small set of primitives under it: one tool registry, one agent step loop, one memory store, one secret store, one approval gate, one scheduler, and adapters to every harness already on the PC. OnQ already has many of these in narrow form. The big missing pieces are a generic tool registry, an MCP client, a real agent loop that calls tools, and any way to reach OnQ from a phone or another PC.

## 3. "Must be one harness": minimum primitives for OnQ

Goal: OnQ is one harness on the PC. Claude Code, Codex, ChatGPT desktop, Hermes and OpenBot are engines or peers that OnQ calls. The glasses user talks to OnQ only.

| Primitive | Why it is needed | Status in OnQ today |
|---|---|---|
| Tool registry | One list of typed tools (name, input schema, risk class, needs-approval flag, handler). Every agent, skill, CLI bridge and MCP tool is exposed through it. | **partial.** Tool names exist only as strings in `SPECIALIST_ROSTER.allowedTools` and ad hoc routes. No schema, no shared dispatcher. This is gap number one. |
| Approval gate | Every tool with a side effect passes one gate that stages, shows a short preview, waits for YES, and logs. | **yes.** Staged previews, default NO, undo window, kill switch, L5 block list. |
| Agent step loop | Model proposes a tool call, harness checks policy, runs it, feeds the result back, stops on a step or time cap. | **partial.** Exists only inside `browserAgent.ts` (14 steps). Not generic. |
| Memory | Save, search, include or exclude, with a background extract pass. | **partial.** `MemoryRecord` store and RAG query exist. No extract pass. |
| Secret store | Named secrets with per-tool scope, never sent to the model or the browser. | **partial.** AES-256-GCM vault with fixed fields and log redaction. |
| Provider router | Choose engine, fail over, cool down, fall back to deterministic rules. | **yes** (`modelRouter.ts`, `providerScanner.ts`). |
| Scheduler | Clock and event triggers with missed-run and overlap policy. | **partial.** Interval timer and kill switch only. |
| MCP client | Reach thousands of existing servers without writing adapters. | **no.** |
| Skills loader | Read `SKILL.md` folders and expose them as callable procedures. | **no** (typed records only, not file-based). |
| File access | Read, list, write inside a root, with approval on write. | **partial.** Read-only allow-listed commands. |
| Network calls to installed harnesses | A small adapter per harness: detect, health check, send a task, get a result. | See next table. |

## 4. Honest gaps

Biggest first.

1. **No generic tool registry.** OnQ has many powerful parts, but they are wired by hand. Anything new (MCP, skills, OpenBot) has nowhere clean to plug in. Size M. Do this first.
2. **No MCP client.** OpenBot reaches many services this way. OnQ hand-codes Google, Notion and Telegram. Size M.
3. **No generic agent step loop.** Only the browser agent loops. CLIs run as one-shot text. Size M.
4. **No remote or phone access path.** The glasses app is limited to localhost. A judge with a real G2 needs a documented relay or tunnel. Size M. UNVERIFIED how OpenBot ties its tunnel binary in, so design this ourselves.
5. **Memory is passive.** No automatic fact extraction, no include or exclude, no cursor. Size M.
6. **Skills are in-memory records, not files.** The user's existing `SKILL.md` skills cannot be used. Size S to M.
7. **Routines are thin.** No missed-run or overlap policy, no webhook trigger, durable restart behaviour UNVERIFIED. Size S to M.
8. **No OpenBot, ChatGPT desktop or Hermes run adapters.** Detection exists for Hermes only. Size S each, ChatGPT desktop may be impossible.
9. **No computer-use layer.** OpenBot ships a native driver. OnQ should not claim this. Size L.
10. **No transfer or sync.** Not needed for the rubric. A one-file export is enough. Size S.

Things OpenBot does that OnQ should NOT chase before 2026-11-29 19:59 UTC: computer use, remote desktop, site hosting, media generation, CRM, billing, team servers, plugin marketplace. None score under the rubric in `ONQ_WINNING_PLAN.md`. The plan says keep the hero on read-and-write plus Telegram, and keep engineering under one collapsed section.

Where OnQ is already ahead: default-NO writes with undo across Calendar, Gmail, Notion and Telegram, a hard block list, owner-only Telegram with watched chats, glance-sized output for a 576x288 display, and a zero-key fallback so a fresh clone passes tests.

## 5. Method limits and UNVERIFIED items

- Counts of words like WhatsApp or Signal in the OpenBot bundle are inflated by libraries. Treat messaging support beyond Slack, Discord, Telegram and GitHub as UNVERIFIED.
- How OpenBot uses cloudflared, how its phone link authenticates, and how its approval automation rules work were not verified. Only names and setting keys were seen.
- Failover details (what exactly carries over to the backup provider) come from the public page and folder names, not code.
- Public docs: `https://openbot.run/` was read. `https://openbot.run/docs` returned 404. No other pages were fetched.
- `@electron/asar` was not installed, so the file index was parsed directly from the archive header. Nothing was extracted.
- OnQ depth checks were quick reads of file outlines. Claims marked "yes" mean the code path exists, not that it was run for this report.
- Nothing here was tested end to end. No command was run against OpenBot.
